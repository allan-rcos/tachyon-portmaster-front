# i18n

O projeto fala **pt-BR (base), en e es**. Duas regras sustentam tudo:

1. **O locale é sempre explícito.** Nada de estado global ou detecção
   implícita: `m.chave({}, { locale })`. É o que permite renderizar o mesmo
   componente em locales diferentes no mesmo processo.
2. **O contrato é bilateral e verificado.** Um `*.messages.schema.json` valida
   ao mesmo tempo os catálogos e o resolver que os consome.

Fonte, pipeline e o validador estão em
[`packages/tachyon-portmaster-i18n`](../../packages/tachyon-portmaster-i18n/README.md).

## Onde cada peça mora

| Peça                 | Lugar                                            |
| -------------------- | ------------------------------------------------ |
| Catálogos por locale | `packages/tachyon-portmaster-i18n/messages/`     |
| Saída compilada      | `dist/paraglide/` (build; alias `@/paraglide/*`) |
| Resolvers de rota    | `src/viewmodel/<feature>/i18n/*.messages.ts`     |
| Contratos de texto   | `src/viewmodel/<feature>/i18n/text-contracts.ts` |
| Termos transversais  | `src/viewmodel/core/i18n/common.ts`              |

O **contrato mora no ViewModel**, não no componente: quem produz o texto é o
ViewModel, e a View o consome. Ver
[a arquitetura](../architecture/mvvm.md#o-contrato-de-texto-mora-no-viewmodel).

## Adicionar uma mensagem

1. Acrescente a chave nos **três** catálogos — faltar em um é erro fatal.
2. Declare-a no `*.messages.schema.json` da rota que a consome.
3. Referencie no resolver irmão: `minhaChave: m.minha_chave({}, { locale })`.
4. `bun run i18n:compile && bun run i18n:check`.

O `i18n:check` reprova nos dois sentidos: chave usada e não declarada, **e**
chave declarada e não usada. É o que impede o catálogo de acumular lixo.

## Como o texto chega na tela

```
catálogo → resolver(locale) → t: MinhaTelaText → props do componente
```

O ViewModel resolve uma vez, no `create*VM`, e o `t` desce por props. Islands e
componentes **nunca** chamam `m.*` — só o resolver chama.

## Locale no servidor e no navegador

`contextLocale(context)` escolhe a origem: header no SSR, `document.cookie` no
navegador. É o mesmo mecanismo que faz uma tela funcionar dos dois lados sem
mudar código.

O cookie é `flow-locale`; sem ele, cai em pt-BR.

## Adicionar um locale

1. Inclua o código em `project.inlang/settings.json` (`locales`).
2. Crie `messages/<locale>.json` completo.
3. Estenda o tipo `Locale` em `src/viewmodel/core/i18n/locale.ts`.

O `i18n:check` passa a exigir o novo locale automaticamente.

## Pendência conhecida

`src/viewmodel/core/i18n/labels.ts` ainda tem **rótulos pt-BR fixos** para os
enums do domínio: status de contêiner, classe de risco, evento de telemetria e
as 24 permissões. São ~43 termos consumidos por 6 componentes (badges, matriz de
permissões, select de risco).

Migrar exige transformá-los num resolver por locale e passá-los por props, como
o resto do texto. Enquanto isso não acontece, **essas etiquetas aparecem em
português mesmo com o locale em `en` ou `es`** — o resto da interface traduz
normalmente.
